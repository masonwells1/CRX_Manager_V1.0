## The finding — REAL, and PRE-EXISTING on `main`

`src/pages/OrderDetail.tsx:80`

```ts
const consolidateIdem = useIdempotencyKey('consolidate_draft_invoices', profile?.id || '');
```

`handleConsolidateDrafts` (line ~1072) retains the key across the result check — `resetKey()`
sits after `assertRpcResult` — but the key carries **no intent scope**. Detail pages do not
remount when the route id changes (no `<x>/:id` route in `src/App.tsx` is rendered with a React
`key`), and `check_idempotency` matches on key + operation **without inspecting `p_order_id`**.

Failure path: ambiguous reply while consolidating order A → key retained → user navigates to
order B → clicks Consolidate → same key → server returns A's cached success → the toast reports
"Consolidated N draft invoices into one" while **B's drafts are untouched**.

**`6ea73628c` goes stale the instant the fix lands.** Every SHA in this document describes the
pre-fix candidate. Re-read live state before acting on any of it.

**This is the LIVE RESIDUAL, which is why it is worth fixing rather than noting.** On `main`
today none of `OrderDetail`'s seven idempotency keys is order-scoped — the scoping IS #584, still
unmerged. #584 scopes three of them. `consolidate_draft_invoices` would **still be unscoped after
#584 merges**, so merging as-is ships a page where three sibling buttons are protected and the
fourth is not.

**Not a regression from #584.** `git show origin/main:src/pages/OrderDetail.tsx` line 1033 already
has `consolidateIdem.resetKey()` after the assert. This PR left it alone. What the PR *did* do is
scope its three siblings with the identical fixed-payload profile and skip this one:

| line | key | RPC payload | scoped? |
|---|---|---|---|
| 77 | `cancelOrderIdem` | `(p_order_id, p_performed_by, p_idempotency_key)` | yes, `id ?? ''` |
| 78 | `createInvoiceIdem` | `(p_order_id, p_salesman_id, p_invoice_type, p_idempotency_key)` | yes, `id ?? ''` |
| 83 | `splitInvoiceIdem` | order-scoped | yes, `id ?? ''` |
| **80** | **`consolidateIdem`** | **`(p_order_id, p_performed_by, p_idempotency_key)`** | **NO** |

The static guard in `src/__tests__/idempotency-reset-order.test.ts` missed it because the guard
checks *reset placement* (reset-before-assert) and never checks whether an already-**retained**
key is scoped. That is the "a guard that pins ONE HALF of a pairing is satisfied by the bug"
failure mode for the fifth time on this PR.
