#### B1 — full rationale

The hook at `.claude/hooks/idempotency-body-check.mjs:55-60` checks for the literal table pattern `FROM idempotency_keys WHERE idempotency_key = p_idempotency_key` and `INSERT INTO idempotency_keys`. Codex's migration uses the canonical helpers (`check_idempotency()` / `save_idempotency()`) exclusively — 17 calls, zero direct table writes. Without the file-level exempt marker, any future Edit/Write on this file via Claude Code is blocked. CLAUDE.md mandates the marker for the helper pattern. Precedent at `20260513020000:2` (canonical commission math).

#### B2 — full rationale

Codex's rewrite at `src/pages/CustomerDetail.tsx:268` replaced:
```ts
const [agingRes, txnRes, prepayRes] = await Promise.all([...]);
```
with 3 sequential `await supabase.rpc(...)` calls. The 3 calls have no data dependencies (different RPCs against different tables). On a slow connection this is a 3× wait. The `assertRpcResult` hardening was correct — it should be kept, but inside the parallelized version.

#### B3 — full rationale

Old version at `20260513020000:75` and follow-up at `20260513090000:47` both declared `SECURITY DEFINER`. Codex's new version is `SECURITY INVOKER`. Functionally equivalent because the 3 wrappers (`convert_quote_to_order`, `create_direct_order`, `create_quick_delivery`) are `postgres`-owned `SECURITY DEFINER` — when they call the helper, `CURRENT_USER` is already `postgres` so the commissions INSERT works either way (postgres owns the table, bypasses RLS). But the change deserves a comment so future readers don't mistake it for a regression.

#### B4 — `execute_sql_readonly` is anon-callable SECURITY DEFINER with arbitrary SELECT capability

**Surfaced by parallel audit session.**

**Live evidence:**
```sql
SELECT proname, prosecdef, has_function_privilege('anon', oid, 'EXECUTE'), r.rolname AS owner
FROM pg_proc p JOIN pg_roles r ON r.oid = p.proowner
WHERE proname='execute_sql_readonly' AND pronamespace='public'::regnamespace;
-- → execute_sql_readonly, prosecdef=t, anon_can_execute=t, owner=postgres
```

**Function body (excerpt):**
```sql
CREATE OR REPLACE FUNCTION public.execute_sql_readonly(sql_query text)
 RETURNS jsonb LANGUAGE plpgsql SECURITY DEFINER SET search_path TO 'public', 'pg_temp'
AS $$ BEGIN
  IF NOT (lower(btrim(sql_query)) LIKE 'select%' OR ... LIKE 'with%') THEN
    RAISE EXCEPTION 'Only SELECT queries are allowed';
  END IF;
  EXECUTE 'SELECT jsonb_agg(row_to_json(t)) FROM (' || sql_query || ') t' INTO v_result;
  RETURN COALESCE(v_result, '[]'::jsonb);
END $$;
```

**Why it matters:** `SECURITY DEFINER` with owner = `postgres` means the embedded `EXECUTE` runs as the table owner, bypassing all RLS. Anon (whose JWT-less key is in the public client bundle) can:
```
supabase.rpc('execute_sql_readonly', { sql_query: 'SELECT * FROM profiles' })
```
and receive every row — email, phone, role — for every user. The SELECT-only restriction does not constrain *which* tables can be read.

**Frontend impact of fixing:** zero. The ONLY caller in the repo is `src/lib/schemaIntegrityLive.test.ts:44`, a dev test that runs against the live DB with the developer's credentials (not anon). Revoking anon EXECUTE does not affect production code paths.

**Why Codex's regex missed it:** prefix is `execute_`, which is not in the regex's alternation list.

**Proposed fix (add to migration 20260526090000):**
```sql
REVOKE EXECUTE ON FUNCTION public.execute_sql_readonly(text) FROM anon, PUBLIC;
```

**Confidence:** High (live grants + body + caller-search all verified).

### 10.8 Implementation correction — B2 reverted to honor coverage convention

During Phase 2 validation of the implementation, the parallel session's vitest suite caught a **regression triggered by B2 itself**:

```
FAIL src/lib/assertRpcCoverage.test.ts > every supabase.rpc() capture must call assertRpcResult (current debt: <=0 files)
Error: assertRpcResult coverage REGRESSED: 1 files have a count mismatch (baseline allows <=0).

[orphan-assert  (assert call without matching RPC capture in same file)]
  src\pages\CustomerDetail.tsx
    captures: 4 (get_fields_with_geojson, save_customer, get_customer_year_end_summary, duplicate_quote)
    asserts:  6
```

**Root cause:** the prior session's B2 fix restored `Promise.all` for the financials-tab parallelism. But the codebase's `assertRpcCoverage.test.ts:76-79` docstring explicitly documents the convention:

> *Avoid `supabase.rpc(...)` inside Promise.all — the regex requires `=` immediately before `await`. Pull the rpc out into its own `const { data } = await supabase.rpc(...)`. (See CustomerContextCard.tsx for the canonical example.)*

The capture regex is `=\s*await\s+supabase\s*\.\s*rpc\s*\(\s*['"]([^'"]+)['"]` — it requires `= await supabase.rpc(...)` directly. `supabase.rpc(...)` inside a Promise.all array literal has no `=` immediately preceding the `await`, so the regex finds the two `assertRpcResult` calls but no matching captures → orphan-assert error → coverage debt > 0 → test fails. Baseline raise requires Mason's explicit sign-off (per the comment at line 57-59), so updating the baseline is not the right fix.

**The prior session's B2 rationale didn't account for this convention.** Re-reading §3.2 B2:
> *"The 3 calls have no data dependencies (different RPCs against different tables). On a slow connection this is a 3× wait. The `assertRpcResult` hardening was correct — it should be kept, but inside the parallelized version."*

Promise.all + assertRpcResult is fundamentally incompatible with this test's regex. The codebase chose **discipline over perf** by ratcheting a 0-baseline coverage test, and the convention is to use sequential `const { data, error } = await supabase.rpc(...)`. So **Codex's original sequential pattern was actually correct**, and the B2 restoration of Promise.all was based on a perf argument that ignored the codebase's documented tradeoff.

**Fix applied:** reverted B2 to sequential awaits with proper destructuring + per-RPC `assertRpcResult` calls (still inside the same try/catch + Sentry wrapper, still inside `if (selectedTab === 'financials')`). Each call now matches the capture regex; 3 captures, 3 asserts, balanced. Inline comment added at the call site documenting why sequential (not Promise.all) is required.

```diff
- const [agingRes, txnRes, prepayRes] = await Promise.all([
-   supabase.rpc('get_ar_aging', { p_as_of_date: today }),
-   supabase.rpc('get_customer_statement', { p_customer_id: id, p_start_date: ninetyDaysAgo, p_end_date: today }),
-   supabase.from('prepay_credits').select('*').eq('customer_id', id!).gt('balance_cents', 0),
```
