BOTH P0 Idempotency replay broken in 5 active mutating RPCs

Pattern: check_idempotency() (20260210000000_tier3_idempotency_and_triggers.sql:36) returns the bare result jsonb (line 53: RETURN v_existing.result;). But these RPCs gate replay on (v_existing->>'status') = 'completed' or 'created', which is always false against the bare result. The branch never fires, the function executes the mutation a second time. The correct pattern (used by record_payment at 20260210000000:100) is IF v_cached_result IS NOT NULL THEN RETURN v_cached_result; END IF;.
Active offenders (latest version of each RPC):
  • create_quick_delivery — CODEX — 20260430240000_field_app_workflow_phase12.sql:402
  • record_invoice_payment — CODEX — 20260330200000_prelaunch_final_fixes.sql:51
  • create_prepay_check_splits — PEER — 20260327200000_wave4_security_integrity.sql:251
  • update_order_items — PEER — 20260334000000_fix_order_item_delete_fk_checks.sql:66
  • receive_po_items — PEER — 20260328000000_wave4_remaining_fixes.sql:537
Why it matters: Network retries duplicate financial mutations. Specifically:
  • Quick delivery retry: duplicate order + delivery + invoice + commission rows + prebooked inventory.
  • Invoice payment retry: duplicate payment recorded (invoice may still owe balance, but customer credited twice on cash side).
  • Prepay check retry: duplicate prepay credit (real money).
  • Order edit retry: duplicate item adjustments.
  • PO receive retry: duplicate inventory increase.
Suggested fix: One migration that rewrites the replay block in all 5 functions to the canonical pattern IF v_cached_result IS NOT NULL THEN RETURN v_cached_result; END IF;. Use jsonb-returning helper if needed for callers that expect a UUID rather than the cached jsonb.
Suggested test: One regression test per RPC: same idempotency-key retry leaves exactly one mutation row.

PEER P0 AP RPCs (record_vendor_payment, create_vendor_bill, void_vendor_bill) declare idempotency key but never use it

File:
supabase/migrations/20260331600000_consolidate_all_rpc_overloads.sql:130 (record_vendor_payment), :44 (create_vendor_bill), :218 (void_vendor_bill)
Evidence: Each function signature accepts p_idempotency_key text DEFAULT NULL, but the bodies have zero references to check_idempotency, save_idempotency, or the idempotency_keys table. The parameters are silent no-ops.
Why it matters: A network retry after a successful vendor payment creates a duplicate AP payment row. Real money out the door, twice. The frontend at VendorBillDetail.tsx:113-143 uses useIdempotencyKey('record_vendor_payment', profile?.id) — the hook works as designed but the server ignores the key, so the UX-level protection is illusory. A button loading={paying} flag closes the fast double-click vector but not the network-stall retry vector.
Race condition: Two concurrent transactions reading the same vendor_bills.balance_cents, both passing the amount <= balance guard, both inserting a payment row, both updating the bill. The FOR UPDATE lock serializes them but doesn't dedup — result: balance can go negative, vendor shows over-paid.
Suggested fix: One migration that explicit-rewrites all three with the canonical check_idempotency / save_idempotency helper pattern. Add SET search_path = public, pg_temp. Add a unique partial index on vendor_payments(vendor_bill_id, idempotency_key) WHERE idempotency_key IS NOT NULL as a defense-in-depth backstop. (See P1 and P2 findings below for the related closed-period and audit-log gaps in these same RPCs.)
Suggested test: Same-key retry creates exactly one row across vendor_payments, vendor_bills updates, and idempotency_keys.

P1 Findings (6)

PEER P1 AP payments bypass the closed-period guardrail

File:
supabase/migrations/20260331600000_consolidate_all_rpc_overloads.sql:130-207 (record_vendor_payment body)
Evidence: The body never calls check_period_open(). AR-side payment RPCs (record_invoice_payment, allocate_payment) DO enforce closed-period locking. create_vendor_bill and void_vendor_bill have the same omission.
Why it matters: CLAUDE.md hard red line: "NEVER bypass check_period_open() — closed periods block backdated transactions." A user can record a vendor payment dated into a closed accounting month, throwing AP off the books for that period without any prompt or warning. This silently breaks month-end reconciliation against bank statements.
Suggested fix: Add PERFORM check_period_open(p_payment_date::date); at the top of record_vendor_payment (after the role check). Same for create_vendor_bill (use bill date) and void_vendor_bill (use original bill date or today, whichever is in a closed period).
Suggested test: Try to record a vendor payment dated into a closed period → should reject. Same period, open → should succeed.

PEER P1 AP money movements are not in financial_audit_log

File:
supabase/migrations/20260331600000_consolidate_all_rpc_overloads.sql:130-207, :44-116, :218-258
Evidence: AR-side RPCs (record_invoice_payment, post_invoice, write-offs) all INSERT INTO financial_audit_log as part of every mutation. The three AP RPCs (record_vendor_payment, create_vendor_bill, void_vendor_bill) write zero rows to that log.
Why it matters: The append-only financial_audit_log is the immutable trail for money flow. Without entries, there is no forensic record of who recorded what vendor payment, when, against which bill. If a duplicate-payment incident occurred (see P0 above), reconstruction would require reverse-engineering from vendor_payments.recorded_at + activity_feed — both mutable.
Suggested fix: Add INSERT INTO financial_audit_log (operation_type, entity_type, entity_id, actor_role, new_values, total_impact_cents, description) to each of the three AP RPCs, modeled on the existing pattern in record_invoice_payment:113-128.

CODEX P1 Quick delivery credit-limit check ignores drafts and the new sale

File:
supabase/migrations/20260430240000_field_app_workflow_phase12.sql:421
Evidence: The credit-limit query sums only WHERE status = 'posted' and rejects only when existing AR ≥ limit. Draft invoices, overdue invoices, and the new delivery's projected total are not included.
Why it matters: A customer can be pushed past their credit limit through quick delivery, especially when several deliveries fire before any invoice is posted.
Mason's decision (Q4): Soft warn, do not block. The RPC should still create the delivery, but post a notification to admins when the projected total + AR balance exceeds the credit limit. Use the same notification pattern that the closed-period warnings use.
Suggested fix: Replace the RAISE EXCEPTION with an INSERT into notifications for each admin (and the activity_feed entry for audit trail). Include posted + overdue + draft + the projected new total in the math.
Suggested test: Over-limit quick delivery succeeds AND fires admin notification; under-limit quick delivery succeeds with no notification.

CODEX P1 Drivers and applicators can read all customers via RLS

File:
supabase/migrations/20260214210000_applicator_role_expansion.sql:59
Evidence: customers_select policy allows is_driver() and is_applicator() with no scope. Verified no later migration overrides this. Policy returns every customer row including PII (contact_name, phone, email, billing_address, credit_terms).
Why it matters: A driver or applicator who knows how to query Supabase directly can dump the entire customer list. The frontend doesn't expose this, but the role boundary is at the RLS layer, not the UI.
Mason's decision (Q2): Option B — drivers and applicators see today's route + customers tied to deliveries/jobs they're assigned to (broader than strict per-record but narrower than today's "all").
Suggested fix: New RLS policy with USING clause:
  • Drivers: EXISTS (SELECT 1 FROM deliveries d WHERE d.customer_id = customers.id AND d.assigned_driver = auth.uid() AND d.scheduled_date >= CURRENT_DATE - INTERVAL '1 day')
  • Applicators: EXISTS (SELECT 1 FROM jobs j WHERE j.customer_id = customers.id AND j.applicator_id = auth.uid() AND j.scheduled_date >= CURRENT_DATE - INTERVAL '7 days') — window adjustable.
Suggested test: RLS test where a driver/applicator reads only their assigned-customer rows; assigned and unassigned customers both verified.

PEER P1 profiles_select USING (true) exposes profile rows to all authenticated callers

File:
supabase/migrations/20260210_fix_rls_critical_issues.sql:56-59
Evidence: The policy permits any authenticated user to select every profiles row. The profiles table holds applicator_license_number, faa_certificate_number, phone, plus any user metadata. Policy comment says "profile names are not sensitive in a CRM context" — understated for the rest of the columns.
Why it matters: Same shape as the customer RLS issue. A non-admin can dump applicator licenses (regulated data).
Mason's decision (Q3): Use the safer default. Default policy: authenticated users see admin and sales-rep profiles for assignment lookup; full PII is admin-only.
Suggested fix: Replace USING (true) with two policies:
  • Public profile fields (id, full_name, role, is_active) visible to all authenticated.
  • License numbers, FAA certs, phone, address visible only to admins or the user themselves (id = auth.uid()).
Probably easier to add a profile_public_view view and revoke direct table SELECT for non-admins. Frontend would query the view.
Suggested test: Sales rep cannot SELECT another user's license number; admin can.

Q8 Phase 1: Vendor Chain Deep-Dive

Mason flagged that he hadn't used the vendor-payment workflow much and asked for a deeper look. Result: the entire AP RPC trio (record_vendor_payment, create_vendor_bill, void_vendor_bill) shares three flaws beyond the single-finding scope of Codex's report. All three are now folded into the findings above; this section explains the systemic picture.

The shape of the gap

The AR (accounts receivable) and AP (accounts payable) sides of the codebase look like mirror images at the schema level — bills/invoices, payments tables on both sides, lifecycle fields, similar mutations. But at the RPC body level, they are very different:

Guarantee AR side (invoices / record_invoice_payment) AP side (vendor bills / record_vendor_payment)
Idempotency replay protectionBroken pattern (CLAUDE.md broken-replay class)Parameter accepted, not used at all
check_period_open() guardYes (line 58 of record_invoice_payment)None
financial_audit_log entryYes (line 113)None
Role checkAdmin or sales_repAdmin only
Money handling (cents bigint)CorrectCorrect
RLS on tablesAdmin-gatedAdmin-gated (verified clean)
Frontend idempotency hookUsedUsed (but server ignores key — illusory)
Test coverageSome unit testsZero E2E or unit tests

Why this matters even though Mason hasn't used it much

The historical exposure is small — few real vendor payments have flowed through this code. But three of the flaws are data-integrity flaws, not just convenience flaws. Once the workflow gets used regularly:

  • Backdated AP into a closed period silently breaks month-end reconciliation against the bank statement, with no warning to the user.
  • No audit log means a duplicate-payment incident cannot be reconstructed forensically — the only trace is in mutable tables.
  • The "same idempotency-key replay" race condition is real even at low volume because slow networks (rural cell tower, intermittent wi-fi) increase retry probability per click.

The risk profile is "low probability of triggering today, high blast radius if triggered, and very hard to forensically reconstruct." That's the opposite of what you want for a money-out workflow.

Single-migration fix

All three RPCs can be fixed in one migration that explicit-rewrites record_vendor_payment, create_vendor_bill, and void_vendor_bill with: canonical idempotency, check_period_open() guards, financial_audit_log inserts, and SET search_path = public, pg_temp. Plus a UNIQUE (vendor_bill_id, idempotency_key) WHERE idempotency_key IS NOT NULL index as defense-in-depth, plus one E2E test that asserts retry produces one row. Estimate: 3–4 hours including the test. Sized as Phase 1 #4 in the fix order below.

Systemic Concerns (the parallel-universe insight)

AP is structurally disconnected from the rest of the financial framework. AR (invoices, payments, allocations) is wired into financial_audit_log, activity_feed, check_period_open(), and the idempotency helpers. AP is wired into none of them. AP rolled out in March 2026 (20260307) and no consolidation pass ever integrated it. Every finding above is a symptom of this single root: AP was never finished.
  • No GL / chart of accounts. Searched whole repo for chart_of_accounts, gl_account, general_ledger, cogs, 1099 — zero mentions. AP recordings hit nothing besides vendor_bills and vendor_payments. CRX is single-entry bookkeeping for AP/AR — no offsetting credits, no double-entry. This is a major architectural choice worth flagging out loud.
  • No bank reconciliation primitive. vendor_payments has payment_method, reference_number, payment_date, amount_cents — but no bank_account_id, no reconciled_at, no cleared_date. Mason can't match cleared checks to a bank statement.
  • vendor_bills schema is impoverished compared to invoices. Invoices have line items (invoice_items), tax fields, GENERATED balance, audit log integration, period gating. Vendor bills are flat: subtotal + adjustment + total + paid + balance, all manually maintained. No itemization means cost-per-product attribution is impossible.
  • No vendor master-data UI. Searched for from('vendors').update, insert, delete in src/pages/ — zero results. The vendors table exists, gets populated by backfill from PO TEXT strings, but has no UI to edit. Mason cannot change a vendor name, terms, or address through the app.
  • No purchasing role. Profile roles are admin, sales_rep, driver, applicator. No purchasing-manager. AP is admin-only. PO creation is admin+sales_rep.

Out of Scope but Worth Knowing

  • No 1099 tracking. No tax_id on vendors, no is_1099_eligible flag, no annual aggregation RPC. End-of-year 1099 prep would require manual SQL.
  • No FIFO / weighted-average inventory costing. Inventory has a single unit_cost field. If 100 units are received at $10, then 100 at $12, there is no cost layering. COGS calculations against this number are approximate.
  • Only two AP report RPCs: get_ap_aging and get_ap_dashboard_summary. No vendor payment history, no top vendors by spend, no purchases by period.
  • Backfill of vendors from purchase_orders.vendor TEXT is fragile. Different PO entries with slightly different spellings created different vendor records during the 20260307100000 migration. Some manual cleanup may be needed.

What AP Gets Right

To avoid breaking these in the fix:

  1. record_vendor_payment uses FOR UPDATE row lock to serialize concurrent payments.
  2. Rejects zero/negative payment amounts and over-payment with clear errors.
  3. void_vendor_bill correctly blocks partially_paid — preventing the orphan-payments bug for that case.
  4. PO → bill linkage is nullable, supporting both PO-derived and manual bills.
  5. vendor_bills has soft delete + admin-only delete RLS — preserves history.
  6. Frontend already wires useIdempotencyKey + assertRpcResult — the moment the server side is fixed, the frontend already participates.
  7. AP aging math correctly excludes voided bills.
  8. vendor_bills.purchase_order_id is nullable + indexed.
  9. Both bill and payment use bigint cents — no float drift.
  10. vendor_payments.created_by = auth.uid() on row creation.
