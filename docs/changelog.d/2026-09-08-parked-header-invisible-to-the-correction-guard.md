## 2026-09-08 — a parked migration header the correction guard could not see, hidden by a conflicted PR

`supabase/migrations/20260908120000_close_pr535_live_gaps.sql` carried a parked-status
header that the repository's own recognizer did not accept, so the file was invisible to
the parked-migration scan while `docs/reference/migration-history.md` row 923 still
declared it a LOCAL CANDIDATE. The guard-hook regression suite failed with:

```
parked marker and LOCAL CANDIDATE history registry are not one-to-one
```

### What was wrong

`hasExplicitParkedMigrationHeader` accepts `PARKED` followed **directly** by `NOT APPLIED`
or `DO NOT APPLY`, separated only by `/`, `-` or an em dash. The header read:

```
-- PARKED - PR #535 follow-up. NOT APPLIED LIVE. Requires Mason's explicit approval
```

which puts the PR reference between the two halves the recognizer pairs. Both phrases are
present and a human reads the file as plainly parked; the recognizer does not. Nothing
about the SQL, the policy, or the parked status was wrong — only the word order in one
comment line.

It now reads `-- PARKED - NOT APPLIED LIVE. PR #535 follow-up. …` and the file carries a
comment saying that order is load-bearing, so it is not tidied back into prose later. The
SQL body is unchanged: the file is regenerated by the same generator, which still asserts
the live body md5 `6d1cab7c4298de34341d517265499896` before substituting.

### Why nobody saw it for two commits

This was the branch's first real CI run in a while. **A CONFLICTING pull request makes
GitHub skip the entire workflow** — the job does not turn red, it does not appear at all,
and the checks that do report (CodeQL, Vercel, the review gates) read green. The failure
had been present since the first commit of this work behind a wall of unrelated passes.
A green check list on a conflicted PR proves nothing about the jobs that never ran.

### The verification lesson

`npm test` is vitest and does **not** run the node-based guard suite. The suite CI failed
on is `npm run test:correction-guards`, and it is the one that must run before calling a
migration change green. Both guards were then re-run against the committed index blob:

- `validateParkedMigrationCrossReferences` returns state `known` (was `unknown`).
- `assertWrappable` still returns OK, so the separate transaction-control fix is intact.
- `npm run test:correction-guards` passes end to end, exit 0.

### Not changed

No recognizer, hook, or CI configuration was touched. The guard was right and the file was
wrong; widening the recognizer to accept the looser wording would have made a
parked-status header easier to write and easier to get subtly wrong, which is the opposite
of what it is for.
